## 1. Как работает аватар клиента

Аватар — не отдельный сервис и не жёсткая конечная автоматика. Сейчас это LLM-агент, которому на каждом ходе передают профиль клиента, релевантную историю диалога и новую реплику Relationship Manager (RM).

### Один ход диалога

1. RM отправляет `message`; если `scenario_id` отсутствует, создаётся новый сценарий.
2. `AgentService` извлекает из SQLite последнее окно истории и, в режиме `sqlite_vec`, несколько семантически близких ранних реплик той же сессии.
3. Собирается prompt: `customer.md` + найденный контекст + история + новая реплика RM.
4. Через `ChatOpenAI` вызывается выбранная OpenAI-совместимая модель.
5. Модель должна вернуть `AgentResponseData`: видимую реплику `reply`, скрытое намерение (`intetions` — текущее имя поля в runtime-контракте), `state`, `trust`, `purchase_probability` и `done`.
6. Pydantic проверяет типы и границы числовых полей. Затем вопрос RM и полный JSON-ответ клиента сохраняются в SQLite.
7. Frontend показывает только `reply`; API при этом возвращает и служебный сигнал. После `done: true` UI автоматически запрашивает отчёт супервайзера.

### Важное ограничение: state machine пока нет

Поля `state`, `trust`, `purchase_probability` и `done` генерирует сама LLM. Код проверяет их допустимый формат, но не проверяет допустимые переходы и не использует эти значения как источник истины для следующего хода. Поэтому это полезный сигнал симуляции, а не детерминированная модель состояния клиента.

Чтобы ввести управляемую state machine, нужно отдельно определить состояния, разрешённые переходы и правила их проверки; результат LLM должен предлагать переход, а код — принимать или отклонять его. Это целевое развитие, а не текущая функциональность.

## 2. Персоны и сценарии как управляемые артефакты

### В текущей реализации `backend/agent/customer.md` одновременно содержит:

- факты персоны: опыт, капитал, текущий брокер, предпочтения;
- голос и поведение клиента;
- возражения и скрытые потребности;
- траекторию конкретного сценария продажи.

### Как создавать и изменять артефакты без рассинхронизации

1. Владелец домена создаёт новую персону или сценарий в статусе `draft`. У каждого артефакта есть ID, версия, владелец и краткое обоснование изменений.
2. Автоматическая проверка валидирует схему, ссылки, уникальность ID, совместимость версий и полноту обязательных полей.
3. Изменение проходит review специалиста по продажам и compliance. Для существенных изменений добавляется или корректируется тестовый кейс.
4. На фиксированном наборе данных запускается evaluation; результат сравнивается с baseline. Только затем bundle получает статус `approved` и может попасть в production.
5. При старте сессии runtime-resolver выбирает bundle и сохраняет его точные ID и версии в сценарии и trace. До конца сессии bundle не меняется.
6. Новая версия публикуется как новая, а не редактирует старую. Это даёт воспроизводимость старых диалогов, changelog и быстрый rollback.

Такой подход устраняет копирование фактов между prompt, runtime и тестами: тест ссылается на тот же versioned bundle, а не содержит собственную версию персоны.

## 3. Откуда берётся оценка и почему ей можно доверять

В проекте есть три разных вида «оценки». Их нельзя смешивать.

| Вид | Источник | Для чего пригоден | Чего не доказывает |
| --- | --- | --- | --- |
| Сигнал клиента | `state`, `trust`, `purchase_probability`, `done` из клиентской LLM | Обратная связь внутри симуляции | Независимое качество RM |
| Отчёт супервайзера | LLM по полному диалогу, `supervisor.md` и контракту | Коучинг: общий балл, разбор реплик, рекомендации | Объективную истину о качестве продажи |
| Offline-evaluation | Детерминированные проверки и LLM-judge на версиях датасетов | Сравнение моделей, prompt и конфигураций | Качество каждого реального разговора |

### Как формируется отчёт супервайзера

По запросу `POST /api/v1/scenarios/{id}/analysis` сервис берёт **всю видимую историю** конкретного сценария, а не только окно памяти. В prompt входят:

- правила sales-coaching из `backend/agent/supervisor.md`;
- профиль клиента из `backend/agent/customer.md`;
- машиночитаемый контракт отчёта;
- пронумерованная последовательность реплик RM и клиента.

Та же LLM возвращает `SupervisorAnalysisData`: общий балл 0–100, итоговый комментарий, оценку или сигнал 0–10 для каждой реплики и приоритетные рекомендации. Код проверяет, что разобрана каждая реплика, сохранены порядок и говорящий, а человекочитаемый текст написан по-русски. При нарушении этих условий выполняется один повтор с усиленным контрактом.

Это сильная проверка **формы**, но не смысла. Оценка не является независимой: клиент и супервайзер используют один и тот же настроенный app-model, а обоснованность балла, полнота rubric и фактологическая корректность автоматически не верифицируются. Поэтому сейчас её правильно использовать как coaching-сигнал, а не как KPI, рейтинг сотрудников или основание для кадрового решения.

### Что должно стать основанием для доверия

Чтобы сделать оценку контролируемой, нужны следующие условия:

- репрезентативный, размеченный экспертами golden set диалогов по каждому типу сценария;
- калибровка LLM-judge против независимых оценок экспертов: расхождения, ложноположительные и ложноотрицательные решения;
- независимый judge-модель или слепая двойная человеческая проверка для контрольной выборки;
- зафиксированные пороги качества и процесс разбора расхождений;
- разделение режима coaching и режима управленческой отчётности.

Доверять стоит не одному числу, а воспроизводимому процессу: измеренному согласию с экспертами, истории изменений и возможности объяснить конкретную рекомендацию через реплики диалога.

## 4. Как проверять работу системы и ловить регрессии

### Реализованные контуры

1. **Contract tests.** `pytest -q tests` проверяет API, SQLite-хранилище, Pydantic-схемы, ошибки структуры, правила и логику повтора отчёта супервайзера. Эти тесты офлайн и детерминированы.
2. **Offline-evaluation.** В `evals/` есть пять наборов данных и 30 кейсов: базовые диалоги, возражения, агрессивные продажи, длинные разговоры и консистентность. Детерминированные evaluators проверяют структуру, ограничения полей, `done`, role break и утечки prompt. LLM-judges оценивают соблюдение персоны, реалистичность, согласованность intentions и траекторию диалога.
3. **Повторные прогоны и сравнение.** `python -m evals.cli run --dataset all --runs N` собирает pass rate, средние, минимум, максимум и разброс. `python -m evals.cli compare <baseline> <candidate>` выявляет регрессии качества, задержки, токенов и стоимости.
4. **Production observability.** При настроенном Langfuse каждый клиентский turn связан по `scenario_id`; сохраняются агент, retriever и generation. Перед экспортом маскируются распространённые PII и credential-пары.

### Ограничения текущей проверки

- Offline-evaluation намеренно изолирован от `AgentService`: он проверяет поведение клиента через отдельный harness, но не доказывает полное совпадение с runtime-пайплайном.
- Runtime-контракт использует поле `intetions`, а evaluation-контракт — `intentions`. Это нужно унифицировать в общем версионируемом пакете схем до появления нескольких артефактов.
- Версии model, prompt и dataset записываются в результаты eval, но их совместимость не проверяется автоматически при сравнении.
- Нет CI workflow, который запускал бы tests и evals на pull request и блокировал promotion при превышении согласованных порогов.

### Целевой release gate

Для каждого изменения кода, prompt, персоны, сценария, rubric, модели или настроек нужен один путь:

```text
Изменение → contract tests → eval против baseline → review → CI gate →
immutable release bundle → production monitoring → feedback в dataset → следующая версия
```

Минимальные правила gate:

- любой критический структурный или compliance-fail блокирует выпуск;
- regression в pass rate или judge-score выше утверждённого порога блокирует выпуск либо требует явного approval;
- baseline и candidate должны использовать совместимые версии датасета, rubric, prompt и модели;
- после выпуска должны быть доступны bundle ID, trace, changelog и rollback на предыдущую версию;
- реальные инциденты и экспертские замечания превращаются в reviewed test cases до следующего релиза.

У стохастической LLM не бывает абсолютной гарантии правильности. Практическую гарантию дают контракты, версии, экспертно откалиброванные evals, CI-gate, наблюдаемость и быстрый rollback.
