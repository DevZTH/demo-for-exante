# Scenario: Агент клиента EXANTE для frontend-разработчика

Этот сценарий нужен для симуляции разговора с потенциальным клиентом брокера EXANTE. В роли клиента выступает агент, описанный в `backend/agent/customer.md`.

Цель — не продать клиента автоматически, а имитировать реальное поведение частного инвестора: отвечать на вопросы, сомневаться, задавать уточнения, менять отношение к продукту и в отдельных случаях соглашаться на следующий шаг.

## 1. Основной endpoint

Для frontend используется путь:

POST /api/v1/scenarios/turns

### Пример запроса

```json
{
  "message": "Здравствуйте, я интересуюсь вашим брокером.",
  "scenario_id": "session_123"
}
```

### Пример ответа

```json
{
  "scenario": {
    "id": "session_123",
    "title": "Здравствуйте, я интересуюсь вашим брокером.",
    "created_at": "2026-08-29T00:00:00",
    "updated_at": "2026-08-29T00:00:00"
  },
  "user_message": {
    "id": 1,
    "chat_id": "session_123",
    "role": "user",
    "content": "Здравствуйте, я интересуюсь вашим брокером.",
    "created_at": "2026-08-29T00:00:00",

  "assistant_message": {
    "id": 2,
    "chat_id": "session_123",
    "role": "assistant",
    "content": "Привет. Я смотрел на EXANTE, но пока не понимаю, зачем мне менять текущего брокера.",

```

## 2. Что считать "видимым" ответом клиента

Frontend должен показывать пользователю только поле:

- `agent_response.reply`

Это та реплика, которую говорит клиент в чате.

Не показывайте скрытую служебную информацию:

- `intetions`
- `state`
- `trust`
- `purchase_probability`
- `done`

Если вы хотите отображать внутреннее состояние в админ-режиме, делайте это отдельно и явно, не смешивая с пользовательским интерфейсом.

## 3. Что важно для UI логики

### 3.1 Состояния клиента

`state` может быть одним из:

- `curious` — просто изучает
- `considering` — думает, может быть полезно
- `interested` — заметил реальную пользу
- `evaluating` — хочет конкретику: комиссии, инструменты, безопасность, демо
- `ready_for_next_step` — готов на следующий шаг
- `ready_to_fund` — готов обсуждать депозит
- `rejected` — отказ

### 3.2 Доверие

Параметр `trust` от 0 до 100.

Используйте его для:

- подсветки статуса клиента;
- отображения уровня доверия в CRM/админ-панели;
- логики "нажать/не нажать" на следующий шаг.

Пример:

- 0–20: сильный скепсис / почти отказ
- 21–40: недоверие, осторожность
- 41–60: нейтрально
- 61–75: продавец вызывает доверие
- 76–100: высокий уровень доверия

### 3.3 Вероятность покупки

`purchase_probability` от 0 до 100.

Используйте его для:

- оценки заинтересованности в конце сценария;
- отображения вероятности дальнейшей сделки;
- внутренних метрик для sales-аналитики.

Важно: это не публичная метрика для клиента, а служебный сигнал для продавца/аналитики.

### 3.4 Флаг завершения

Если `done: true`, сценарий завершён.

Типичные причины:

- клиент отказал;
- клиент потерял доверие;
- достигнут следующий логический шаг;
- клиент готов перейти к onboarding / funding;
- обе стороны понимают, что продукт клиенту сейчас не подходит.

## 4. Как читать поведение клиента

Для frontend логики стоит помнить, что агент ведёт себя как реальный частный инвестор:

- он не любит давление;
- не верит маркетинговым обещаниям;
- задаёт вопросы про стоимость, безопасность, понятность платформы;
- интересуется реальной ценностью для его портфеля;
- может отказываться, если продавец говорит в стиле "у вас точно всё получится";
- готов двигаться дальше только при определённой логике и доверии.

## 5. Типовые сценарии

### Сценарий A: клиент изучает

```json
{
  "state": "curious",
  "trust": 52,
  "purchase_probability": 32
}
```

Ожидается нейтральная реакция. Клиент задаёт вопросы, но пока не готов покупать.

### Сценарий B: клиент увидел пользу

```json
{
  "state": "interested",
  "trust": 68,
  "purchase_probability": 55
}
```

Клиент начинает замечать, что продукт может быть полезен. Важно показать конкретику, а не просто общую презентацию.

### Сценарий C: клиент готов к следующему шагу

```json
{
  "state": "ready_for_next_step",
  "trust": 75,
  "purchase_probability": 70
}
```

Клиент готов на демо, pricing, второй звонок, регистрацию или проверку условий.

### Сценарий D: клиент отказывается

```json
{
  "state": "rejected",
  "trust": 12,
  "purchase_probability": 5,
  "done": true
}
```

Нужно завершить сценарий и не пытаться "продавать дальше".

## 6. Рекомендации для frontend

### Для Chat-UI

- Отображайте только `agent_response.reply` как текст сообщения клиента.
- Сохраняйте весь JSON в hidden/technical data, если это нужно для диагностики.
- Если есть кнопки действий ("Далее", "Отправить pricing", "Начать onboarding"), активируйте их только если:
  - `state` в `ready_for_next_step` или `ready_to_fund`;
  - `done` не равно true.

### Для аналитики / CRM

- `trust` используйте в модуле sales-analytics;
- `purchase_probability` — для оценки likelihood;
- `state` — для статуса клиентского сценария;
- `done` — для определения завершённого разговора.

### Для UX

- Не показывайте клиенту скрытые метрики.
- Не заставляйте его проходить сценарий строго до покупки.
- Сохраняйте "естественность" беседы: клиент может сомневаться, задавать вопросы, менять мнение.

## 7. Пример frontend-кода

```javascript
async function sendScenarioMessage(message, scenarioId) {
  const response = await fetch('/api/v1/scenarios/turns', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      message,
      scenario_id: scenarioId,
    }),
  });

  const data = await response.json();

  const customerText = data.agent_response.reply;
  const state = data.agent_response.state;
  const trust = data.agent_response.trust;
  const purchaseProbability = data.agent_response.purchase_probability;
  const isDone = data.agent_response.done;

  return {
    customerText,
    state,
    trust,
    purchaseProbability,
    isDone,
  };
}
```

## 8. Итог

Для frontend разработчика важно понимать одно правило:

- пользовательский интерфейс работает с полем `reply`;
- служебная логика работает с полями `state`, `trust`, `purchase_probability`, `done`;
- сценарий клиента должен вести себя как реальный инвестор, а не как "продажный" бот.

Если нужно, можно сделать отдельный UI-сценарий для:

- чат-диалога с продавцом;
- интерактивного статуса клиента;
- панели аналитики доверия и вероятности продаж.
